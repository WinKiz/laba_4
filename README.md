# Лабораторная №4. Клиент TCP-брокера

Java 21, Maven, пакет `ru.winkiz.lab4`. Клиент поддерживает отправку и фоновый приём кадров `message <число байтов UTF-8>\n<payload>`. Три сценария проверяют сами сообщения, а не только их количество.

Готовый отчёт: [results/local/ОТЧЁТ.md](results/local/ОТЧЁТ.md). Рядом находятся исходные измерения, распределение по получателям, сводная таблица и шесть графиков. [Все 12 ответов](docs/ВОПРОСЫ.md), [проверка требований](docs/ЧЕКЛИСТ.md), [объяснение программы](docs/РАЗБОР.md).

## Что находится в проекте

- `BrokerClient.java` — оцениваемый клиент: соединение, роли, синхронизация, ожидание, ошибки, закрытие.
- `Protocol.java` — чтение/запись кадров и проверка ограничений.
- `ScenarioRunner.java` — три автоматических сценария, дополнительные конфигурации, проверка ID, текстов и метрик.
- `Main.java` — параметры запуска, повторные измерения, код завершения.
- `ReportWriter.java` — CSV, простой текстовый отчёт и PNG-графики.
- `LocalBroker.java` — вспомогательный сервер для разработки. Он добавлен, поскольку сервер преподавателя не предоставлен. Это отдельная часть стенда, она не подменяет реализацию клиента.
- `src/test/.../SelfTest.java` — проверки протокола, отказов, конкурентной отправки и жизненного цикла.

## Самый простой запуск

Нужен **JDK 21 или новее**, а не только JRE. Откройте в IntelliJ IDEA или NetBeans именно каталог с `pom.xml`, дождитесь импорта Maven и запустите `ru.winkiz.lab4.Main` без аргументов.

Main поднимет вспомогательный брокер на свободном локальном порту и выполнит все три сценария: один прогрев и пять измерений каждого. После эксперимента сервер и клиентские потоки закрываются. В конце выводятся общий PASS/FAIL и абсолютный путь к отчёту. Без аргументов результаты сохраняются в новый каталог `results/run-<время>`, старые файлы не перезаписываются.

Нормальное завершение возвращает **0**, провал любого сценария, ошибка параметров или утечка потоков — **1**. Ошибка соединения — FAIL, а не успешная имитация обмена.

## Сборка и тесты

Из папки проекта:

```powershell
mvn package
java -jar target/lab4-broker-client-1.0.jar
```

`mvn package` компилирует программу, запускает SelfTest на фазе `test` и собирает исполняемый JAR. Тесты не требуют внешнего сервера. Для первого Maven-запуска нужен доступ к Maven Central.

SelfTest содержит 28 самостоятельных проверок с явными AssertionError. В выводе Maven строка Surefire `Tests run: 0` относится к отсутствующим JUnit-тестам; ниже должен быть запуск `exec:java (protocol-tests)` и **SELFTEST PASS: 28 checks**. Именно он выполняет сетевые проверки. Ошибка любой из них завершает Maven-сборку неуспешно.

Если Maven не установлен, на Windows:

```powershell
.\build.ps1
java -jar target/lab4-broker-client-1.0.jar
```

Скрипт также проверяет исходники и запускает SelfTest. Путь к `jar.exe` определяется через установленный JDK, поэтому не требуется вручную добавлять этот инструмент в PATH.

## Повтор полного эксперимента

```powershell
java -jar target/lab4-broker-client-1.0.jar --local --full --out results/my-run
```

Выходной каталог должен быть новым или пустым. Полная серия включает 15 конфигураций по 6 запусков: 90 запусков, из них 75 основных измерений.

1. Три обязательных сценария: 1000; 1000 с отключением R1 после 250; 2×1000 с тремя получателями.
2. Два отправителя по 1000 сообщений и 1/2/3/4/6 получателей.
3. Два отправителя по 1000 сообщений, три получателя, полезная нагрузка ровно 16/256/4096/65536 байт.
4. TCP_NODELAY=true/false на клиенте, сообщения по 16 байт.
5. Четыре отправителя и четыре получателя, всего 10 000 сообщений.

Заголовки не входят в размер полезной нагрузки. Стандартные сообщения содержат кириллицу, emoji, перевод строки и NUL. Нагрузки по 16 байт содержат ASCII ID и случайный суффикс, чтобы уложиться в заданную длину.

Примеры настройки:

```powershell
java -jar target/lab4-broker-client-1.0.jar --scenario 3 --messages 2000 --bytes 4096 --timeout 10 --seed 17 --warmups 1 --repeats 5 --out results/custom
java -jar target/lab4-broker-client-1.0.jar --help
```

`--messages` — количество на отправителя. Для сценария 2 число должно делиться на четыре. Изменённые параметры — отдельный эксперимент; нормативный прогон использует значения по умолчанию. `--queue` задаёт префикс, к которому автоматически добавляется уникальный суффикс UUID для каждого запуска.

## Работа с отдельным сервером

Сначала в отдельном терминале запустите **сервер**, затем **клиент**:

```powershell
java -jar target/lab4-broker-client-1.0.jar --server --bind 127.0.0.1 --port 1111
```

```powershell
java -jar target/lab4-broker-client-1.0.jar --host 127.0.0.1 --port 1111 --full --out results/external
```

Для сервера преподавателя используется вторая команда с его адресом. Опция `--host` отключает создание встроенного сервера. Базовый протокол не содержит статусов/ACK. Внешний сервер должен поддерживать именно `message`, длину в байтах и строку настройки из задания.

VPS не требуется условием. Инструкция для будущего размещения: [docs/VPS.md](docs/VPS.md). Развёртывание на реальном VPS сейчас не выполнялось: адрес и доступ ещё отсутствуют.

## Особенность сценария 2

Фоновый поток может заранее принять больше 250 сообщений. Просто вернуть из `receive(250, ...)` первые 250 и выбросить остальные при закрытии было бы ошибкой.

Поэтому до отключения R1 отправитель ждёт обработки предыдущего сообщения, используя монитор и общее состояние теста. После приёма ровно 250 R1 закрывает клиент и открывает CountDownLatch; далее отправитель продолжает. Оба получателя подключаются до отправителя, всего посылается 1000 сообщений. Потери и дубликаты всё равно проверяются.

При закрытии получателя сначала выполняется TCP shutdownOutput: сервер видит EOF, исключает получателя из распределения и закрывает ответную сторону. Клиент ограниченно ждёт завершения reader (до 500 мс), затем в любом случае закрывает сокет. LocalBroker удаляет получателя **до** закрытия ответной стороны. Это устраняет найденную гонку «клиент уже закрылся, сервер ещё выбирает его», без добавления новых команд протокола.

Это управляемый сценарий, а не доказательство доставки ровно один раз при любой аварии. Даже при управляемом закрытии внешний сервер без ACK может иначе обработать гонку отключения. В базовом протоколе нет команды возврата сообщений из буфера клиента или подтверждения регистрации/доставки. Для произвольной быстрой отправки и аварийного отключения требование «250+750 без потерь» невозможно гарантировать одним клиентом. При отличающемся поведении выданного сервера нужен разбор с преподавателем, как прямо требует задание.

## Ограничения и проверенная среда

Максимальный кадр — 1 МиБ, заголовок — 1024 ASCII-байта, имя очереди — латинские буквы, цифры, `_`, `-`. Пустые сообщения и нулевая/отрицательная длина отклоняются. Клиентский буфер ограничен 100 000 сообщениями и 64 МиБ UTF-8; переполнение приостанавливает чтение и создаёт обратное давление. У одной заблокированной отправки есть предел 10 секунд; общий дедлайн сценария по умолчанию также 10 секунд от первой отправки.

Принятые строки хранятся в `ArrayDeque`, все обращения защищены `ReentrantLock`. `Condition` атомарно отпускает замок на время ожидания; ошибки и закрытие будят всех ожидающих. Внутренний контейнер наружу не выдаётся. Для записи используется отдельный замок, поэтому чтение не блокируется ожиданием отправки.

Локальные измерения: Windows 10, JDK 23.0.2, компиляция `--release 21`, 16 логических процессоров. Запуск непосредственно на JVM 21 нужно отличать от проверки совместимости компилятором; актуальная информация о выполненных проверках находится в `results/validation.txt`.

Вспомогательный сервер не имеет дискового хранения, аутентификации или TLS; его очереди живут в памяти процесса. Для VPS предусмотрен доступ через SSH-туннель. Сервер использует round-robin, поэтому доли близки к идеальным по его алгоритму. Результаты loopback не описывают производительность VPS.
