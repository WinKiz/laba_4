# Как устроена лабораторная работа

## Сначала общая идея

Брокер — промежуточный сервер с очередями. Отправитель знает имя очереди, но не адрес получателя. Получатель знает то же имя очереди, но не адрес отправителя. Клиенты устанавливают разные TCP-соединения с одним брокером. Сообщение должен получить один получатель, а не все одновременно: это очередь, а не широковещательная рассылка.

Программа разделена на шесть основных файлов. Это небольшие самостоятельные обязанности, а не отдельный файл для каждой мелкой функции. Тесты стоят отдельно от рабочего кода.

```text
Main → ScenarioRunner → BrokerClient → Protocol → TCP-соединение
  │                           │
  └→ ReportWriter             └→ фоновый reader → очередь → receive

LocalBroker — вспомогательный второй конец TCP-соединения
SelfTest — проверки клиента, включая намеренно плохие ответы
```

## Полезные слова Java

- `class` описывает тип объекта, `new` создаёт конкретный объект.
- `final class` запрещает наследовать класс. `final` у поля запрещает повторно присвоить ссылку, но не делает объект неизменяемым.
- `private` разрешает доступ только внутри класса; `public` открывает внешний интерфейс.
- `static` относится к классу, а не к отдельному объекту. Поэтому Main.main вызывается без создания Main.
- `void` означает отсутствие возвращаемого значения. Это не означает, что метод ничего не делает.
- Конструктор называется так же, как класс, и не имеет типа возвращаемого значения.
- `throws IOException` объявляет возможное исключение. `throw new IOException(...)` действительно создаёт и выбрасывает его.
- `try/finally` гарантирует освобождение замка. `try (resource)` вызывает close у AutoCloseable.
- `record` — компактный класс для набора данных. Его компоненты доступны через методы вроде result.sent(). Массив внутри record сам по себе не становится неизменяемым.
- `enum` — ограниченный набор допустимых значений; Role может быть только SENDER или RECEIVER.
- `() -> ...` — лямбда, передаваемое действие. Например, задача для пула потоков.
- `List<String>` — список строк. `Map<String, Long>` — соответствие строк числам типа Long.
- `volatile` обеспечивает видимость присваиваний между потоками, но не делает составную операцию вроде `x++` атомарной.

## Protocol.java

Этот класс отвечает только за формат байтов на проводе. У него приватный конструктор: создавать экземпляры не требуется, вспомогательные методы static.

`MAX_MESSAGE_BYTES` равен 1 048 576, то есть 1 МиБ. `MAX_HEADER_BYTES` равен 1024. `validateQueue` проверяет разрешённый алфавит имени и длину, чтобы вся строка настройки помещалась в лимит заголовка.

`encode` превращает String из Java в UTF-8-байты. Используется строгий кодировщик: непарный суррогат не заменяется молча знаком вопроса, а вызывает ошибку. Пустой массив и слишком большой массив запрещены.

`writeMessage` сначала пишет ASCII-заголовок, затем исходный массив тела, затем flush. Никакого дополнительного перевода строки после тела нет. Этот метод сам не синхронизируется: блокировку полного кадра обеспечивает BrokerClient.

`readLine` побайтно ищет LF. Это собственный разбор заголовка, а не BufferedReader. Если EOF встретился после части заголовка, выбрасывается EOFException. Если EOF пришёл на границе кадров, возвращается null. Не-ASCII и управляющие байты, в том числе CR, запрещены: протокол задания использует LF.

`readPayload` проверяет полное соответствие заголовка шаблону `message [0-9]+`, разбирает длину как int, проверяет диапазон и вызывает readNBytes. TCP может передать части кадра разными порциями; readNBytes собирает их до N байтов или EOF. После вызова всё равно нужно проверить реальную длину массива.

`decode` строго декодирует UTF-8. Это позволяет заметить ошибку кадрирования, а не получить строку с символами замены.

Пример: `привет` → 12 байтов → `message 12\n` → 12 байтов тела. Следующий кадр может идти сразу после последнего байта тела. Тело `a\nb` не разбивается на два сообщения.

## BrokerClient.java

Это библиотечный клиент. Его назначение — соединиться, отправлять или принимать, ждать и закрываться. Он не знает про 1000 сообщений, распределение 250/750 или построение графиков.

### Состояние объекта

`role` фиксирует роль. `socket`, `in`, `out` относятся к одному соединению. Входной BufferedInputStream единственный. Буферизация не меняет границы кадров: ими управляет Protocol.

`writeLock` защищает одновременные send целиком. `stateLock` защищает очередь, pendingBytes, failure и closed. Это разные замки: закрытие может добраться до сокета, даже когда отправка заблокирована в сети.

`received` — ArrayDeque элементов Received, где есть текст и исходный размер UTF-8. Счётчик pendingBytes нужен для ограничения буфера. Его нельзя надёжно вычислить через String.length: это другая единица измерения.

`changed` — Condition, связанное именно со stateLock. Оно будит receive при сообщении, ошибке и close, а reader — при освобождении места в буфере.

`failure` хранит первую ошибку соединения. `closed` означает намеренное локальное закрытие. Обычный boolean здесь допустим, потому что чтение и запись выполняются под одним замком.

`reader` существует только у получателя. `writeWatchdog` существует только у отправителя. У каждого клиента свои соединение, очередь и средства синхронизации; static IDS лишь выдаёт разные имена потокам.

### Конструктор

Проверяет параметры до подключения. Создаёт TCP-соединение с ограниченным ожиданием, устанавливает TCP_NODELAY, получает потоки, отправляет настройку роли и flush. Для RECEIVER запускает reader. При сбое закрывает сокет и выдаёт IOException с адресом.

Отправка строки настройки не доказывает, что сервер уже её обработал: в задании нет ACK. Создавать ложное «подтверждение сервера» клиент не должен.

### send

Проверяет роль и кодирует текст. Входит в synchronized(writeLock), проверяет состояние под stateLock. Планирует предельное время одной отправки: если write зависнет, watchdog закроет сокет. Затем отправляет полный кадр. Задача watchdog отменяется в finally. Любая IOException сохраняется через fail и выдаётся вызывающему коду.

Важный вопрос: SO_TIMEOUT ограничивает чтение сокета, а не его запись. Поэтому нельзя решить зависание send только вызовом setSoTimeout.

### receive

Проверяет роль, count и Duration. Запоминает System.nanoTime и общий бюджет ожидания. Захватывает stateLock с возможностью прерывания. Пока результат меньше count, проверяет failure/closed, извлекает готовый элемент либо считает оставшееся время и вызывает awaitNanos.

Await освобождает замок на время сна, иначе reader не смог бы добавить сообщение. После пробуждения замок снова удерживается, а условие проверяется повторно. Таймаут общий для пачки: он не начинается заново после каждого сообщения.

Возвращается List.copyOf, а не внутренняя очередь. Если к сроку собралась только часть пачки, эта часть возвращается. Duration.ZERO используется для извлечения уже готовых элементов без ожидания. Отрицательный count или Duration — ошибка параметров, а не сетевой отказ.

### readLoop, fail, checkState

Reader непрерывно читает тело, декодирует строку, ждёт места в ограниченном буфере и добавляет Received под замком. Любой EOF или неверный кадр превращается в сохранённую ошибку. `fail` будит ожидающих и закрывает повреждённый сокет. `checkState` выдаёт новую IOException с исходной причиной в cause.

Тихо написать stack trace из фонового потока недостаточно: основной поток должен узнать, что ожидание уже бессмысленно. Здесь он узнаёт через checkState после signalAll.

### close

Помечает клиент закрытым и будит ожидающих. Для получателя сначала выполняется shutdownOutput: исходящая сторона TCP заканчивается сигналом FIN, но входная ещё может прочитать ответный EOF. Клиент до 500 мс ждёт reader, чтобы сервер успел исключить соединение из распределения. Затем безусловно закрывает сокет, вызывает interrupt и ограниченное ожидание join. Это не сообщение ACK и не подтверждение обработки доставленных данных. Если close случайно вызван самим reader, join самого себя пропускается. Watchdog останавливается и также ожидается. Повторный close допустим. Закрытие не требует захватывать writeLock, иначе зависшая запись могла бы помешать освобождению сокета.

## ScenarioRunner.java

`Options` описывает сервер и общие настройки. `Plan` описывает эксперимент: число отправителей, получателей, размер, TCP_NODELAY. `Result` хранит реальные счётчики и измерения. Внутренний RunState принадлежит одному запуску и не используется следующим.

До запуска готовятся тексты точного размера и expected ID→полный текст. Это вне таймера. У каждого отправителя ID содержит его номер и номер сообщения. Все очереди имеют UUID, поэтому старые сообщения не влияют на новый запуск.

`sentIds` считает успешные возвраты send. Это ещё не доказательство доставки. `seen` — конкурентное множество принятых ID. `record` проверяет неизвестный ID, совпадение текста, повторный ID, увеличивает счётчики и сохраняет время. `missing` в конце — разность expected и seen. PASS возможен только при совпадении множеств, правильном количестве, отсутствии ошибок и повреждений.

`start` одновременно открывает подготовленные задачи. Начало измерения устанавливает первый реально начавший отправку поток непосредственно перед первым send, не основной поток перед созданием клиентов.

### Сценарий 1

Сначала подключён только отправитель. После 500 отправок он открывает firstHalf и ждёт receiverConnected. Основной поток создаёт получателя, запускает его задачу и открывает второй барьер. Отправитель досылает 500. Проверяются все 1000 ID. Пауза и подключение получателя входят в интервал, потому что первая отправка уже была.

### Сценарий 2

Сначала создаются R1 и R2, затем отправитель. До отключения R1 отправитель ждёт отдельный CountDownLatch из processed для предыдущего ID. Получатель открывает его после обновления счётчиков и времени, поэтому видимость записи о получении нельзя перепутать с завершением всей обработки. На 250-м своём сообщении R1 закрывает соединение, открывает firstClosed и завершает свою задачу. Отправитель продолжает, R2 добирает остаток. В конце проверяются не только общие 1000, но и строго 250/750.

Такое управление необходимо из-за фонового чтения: receive(250) не запрещает reader прочитать ещё сообщения. Однако оно не добавляет отсутствующее серверное ACK. Если внешний сервер отправит сообщение в уже закрывающееся соединение, тест честно покажет FAIL. Нельзя объявлять клиенту гарантию, которой исходный протокол не даёт.

### Сценарий 3

Сначала подключаются три получателя и два отправителя. У отправителей разные клиенты, они работают параллельно. Получатели учитывают сообщения до общего ожидаемого числа или общего дедлайна. Распределение не зашито: counts наполняется фактическим приёмом. Для нагрузочного опыта тот же механизм используется с четырьмя отправителями и получателями.

Задачи объединяются через Future.get с оставшимся временем. По окончании есть короткое наблюдение за лишними кадрами, которое не входит в измерение успешной доставки. Затем все клиенты закрываются, пул останавливается и ожидается. Поздний дубликат за пределами конечного окна наблюдения в принципе исключить нельзя никаким конечным тестом.

Время — секунды из наносекунд. X=received/time. Байт/с учитывает payloadBytes, а не длину строки Java. Доли считаются от фактического received. Задержка — от отметки перед send до учёта в record, поэтому включает очередь и планирование. Все метки находятся в одном процессе и используют один nanoTime; часы удалённого VPS для этого не нужны.

## Main.java

Приватный конструктор запрещает ненужные экземпляры Main. main вызывает execute, перехватывает ошибки и завершает процесс кодом 1 при неуспехе. При успехе метод возвращается, и процесс получает 0 естественно.

Parse принимает только перечисленные --параметры, не разрешает повтор одного параметра. Числа и границы проверяются. Без --host запускается локальный брокер; с --host используется только внешний. --server запускает самостоятельный сервер и не выполняет сценарии. --help печатает справку.

По умолчанию строятся три Plan. --full добавляет 12 дополнительных конфигураций. Для каждого плана сначала выполняются warmup, затем measurement. Все сохраняются, но итоговая статистика использует только measurement. Один FAIL делает общий результат неуспешным, даже если следующий повтор прошёл.

Output не должен содержать старые файлы: это предотвращает смешивание разных серий. Environment фиксирует среду и оставшиеся потоки. Для сервера устанавливается shutdown hook, чтобы Ctrl+C вызвал освобождение ресурсов.

## ReportWriter.java

Отделён от сети: только получает список Observation и пишет файлы. Measurements содержит все запуски, Shares — всех получателей каждого запуска. Summary группирует только измерения по имени плана. Медиана берётся из отсортированной выборки, а минимум/максимум показывают разброс.

PNG строятся стандартным Java AWT в BufferedImage, поэтому не нужен Excel, Python или сторонняя библиотека для повторения отчёта. Неуспешные результаты в графике выделяются красным, а в таблице выводится «Ошибка». Подписи графиков и названия экспериментов в отчёте русские. Технические ключи CSV и статусы PASS/FAIL сохраняют общий формат для автоматической проверки. При построении графиков на Linux нужен шрифт с поддержкой кириллицы.

В графиках размеров и числа получателей X — категории. Точки имеют равный экранный шаг; нельзя по наклону линии делать вывод о производной по байтам. Итоговый p95 — медиана p95 запусков, что явно указано в отчёте.

## LocalBroker.java

Не часть оцениваемого клиента. Нужен только потому, что выданного сервера пока нет. Слушает TCP, разбирает настройку, складывает кадры отправителей в именованные Mailbox. У каждой очереди есть ожидающие сообщения и очередь подключённых получателей. Диспетчер выбирает следующего получателя по round-robin, пишет кадр и перемещает получателя в конец списка.

Очередь сохраняет данные при отсутствии получателей. При ошибке записи кадр не удаляется. Успешная запись не считается подтверждением обработки приложением: это ограничение описано в README. Отдельный поток сеанса получателя обнаруживает его EOF, сначала удаляет соединение из списка распределения, а затем закрывает серверный сокет. Такой порядок вместе с ограниченным ожиданием ответного EOF в клиентском close устраняет обнаруженную гонку штатного отключения R1. При закрытии сервера закрываются слушатель, все сокеты и пул.

Приватный bind 127.0.0.1 означает доступ только с того компьютера. 0.0.0.0 означает слушать все IPv4-интерфейсы, но для VPS проще использовать loopback и SSH-туннель.

## SelfTest.java

Это отдельные автоматические проверки с тестовыми TCP-собеседниками. Они умеют намеренно отправить неверный заголовок, оборвать тело, передать несколько кадров подряд, прислать некорректный UTF-8. Это не полная реализация второго брокера.

Самостоятельный разбор исходящих кадров проверяет, что четыре потока на одном клиенте не перемешали заголовки и тела. Есть тесты общего таймаута, частичного результата, неизменяемого возвращаемого списка, неверной роли, повторного close и пробуждения нескольких ожидающих. После интеграционных сценариев проверяется отсутствие именных потоков программы.

Для отказов используются настоящие сокеты и проверки исключений. Expected PASS не рисуется вручную: AssertionError завершает проверку ошибкой, сборка не считается успешной.

## TCP_NODELAY и алгоритм Нейгла

Алгоритм Нейгла может задержать небольшую порцию данных, пока предыдущая не подтверждена TCP или не набрался достаточный объём. Это уменьшает число мелких пакетов. TCP_NODELAY=true отключает этот механизм для исходящих данных данного сокета. Это не доставка с подтверждением приложением и не обещание ускорения во всех случаях.

Flush относится к Java-буферу. Он передаёт накопленное в сокет, но не приказывает сети немедленно доставить пакет и не отключает Нейгла. В полном эксперименте один и тот же сценарий сравнивается с true и false; серверная опция фиксирована. На loopback эффект обычно меньше и сильнее перемешан с планировщиком, чем на удалённой сети.

## Что могут спросить на защите

1. Где вычисляется длина? В Protocol.encode, размер UTF-8 byte[].
2. Где исключено перемешивание кадров? В synchronized(writeLock) в send.
3. Где очередь становится потокобезопасной? Все действия с received проходят под stateLock.
4. Где ждут вместо sleep? changed.awaitNanos/await и CountDownLatch.await.
5. Почему while, а не if? После пробуждения условие могло измениться, возможны ложные пробуждения.
6. Где устанавливается роль? Строка настройки в конструкторе, далее final role и проверки методов.
7. Кто получает ошибку reader? receive через failure/checkState, а не только консоль.
8. Почему нельзя просто interrupt reader? Для освобождения сетевого read надёжно закрывается сокет, затем выполняется interrupt/join.
9. Почему S1/S2 не конфликтуют? У них отдельные клиенты; дополнительный тест проверяет и общий клиент.
10. Что означает PASS? Проверенное конечное множество доставок в конкретном запуске, а не универсальную гарантию сети.
11. Почему ровные доли? LocalBroker использует round-robin; чужой сервер может распределить иначе.
12. Почему времена меньше секунды? Loopback, небольшие сообщения и отсутствие искусственного ожидания. Увеличивать время sleep ради красивого числа неправильно.
13. Чем reset TCP отличается от EOF? Reset обычно даёт IOException, корректное завершение чтения — -1. Оба завершают приём с диагностикой, если соединение не закрыто самим клиентом.
14. В чём разница ACK TCP и ACK приложения? Первый относится к принятым байтам транспортного стека, второй — к принятому/обработанному сообщению на уровне протокола.
15. Где сервер, а где клиент? BrokerClient — клиентская библиотека; LocalBroker — вспомогательный сервер; ScenarioRunner создаёт много клиентов и измеряет их работу.
