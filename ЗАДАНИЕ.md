# Лабораторная работа №4
## Клиент TCP-брокера сообщений

### Цель работы

Изучить практическое применение сокетов, прикладного протокола с передачей длины сообщения, многопоточности и средств синхронизации при разработке клиента брокера сообщений, а также освоить методику автоматизированного тестирования конкурентного сетевого взаимодействия.

В работе необходимо:

- реализовать клиент, поддерживающий роли отправителя и получателя;
- реализовать установку режима работы и кадрирование сообщений по заданному протоколу;
- организовать фоновый приём сообщений;
- обеспечить потокобезопасное хранение принятых сообщений и ожидание с таймаутом;
- корректно завершать соединение и обрабатывать ошибки;
- автоматически выполнить три обязательных сценария тестирования;
- проверить полноту доставки, отсутствие дубликатов и равномерность распределения;
- измерить время работы и пропускную способность;
- оформить отчёт с таблицами, графиками и выводами.

> **Важно.** Сервер брокера выдаётся готовым. Реализация сервера в эту работу не входит и отдельно не оценивается. Оценивается только клиент и корректность его автоматических тестов. Сервер соответствует протоколу, описанному в разделе 2; если поведение сервера расходится с протоколом, сообщите об этом преподавателю.

# 1. Постановка задачи

**Брокер сообщений** — это промежуточная программа, которая обеспечивает обмен сообщениями между другими программами, приложениями или сервисами. Отправитель передаёт сообщение брокеру, а брокер доставляет его получателю.

Брокер позволяет развязать отправителя и получателя:

- им не нужно знать друг о друге;
- им не нужно работать одновременно;
- сообщения могут накапливаться в очереди, пока получатель недоступен.

В работе используется простой брокер, работающий по TCP. Сообщения группируются в именованные очереди. Клиент открывает одно TCP-соединение и работает в одном из двух режимов:

```text
отправитель (send)  ──→  очередь "test1"  ──→  получатель (receive)
```

Режим работы фиксируется на всё время соединения и не может быть изменён.

Схема взаимодействия:

```text
BrokerClient (SENDER)                Broker (сервер)                BrokerClient (RECEIVER)
        │                                  │                                  │
        │──── send test1\n ───────────────→│                                  │
        │──── message 12\nHello world! ───→│                                  │
        │                                  │──── message 12\nHello world! ───→│
        │                                  │                                  │
```

Сообщение, отправленное отправителем, может быть получено **только одним** получателем. Если получателей несколько, сервер распределяет сообщения между ними. Если получателей нет, сообщения накапливаются в очереди и будут доставлены после подключения получателя.

# 2. Протокол

Протокол текстовый, но сообщение передаётся как последовательность байтов, а не символов. Это важно для корректной работы с кириллицей и любыми другими символами за пределами ASCII.

## 2.1. Установка соединения

Клиент открывает TCP-соединение и отправляет одну строку настройки:

```text
send <queue-name>\n
receive <queue-name>\n
```

Пример:

```text
send test1\n
```

означает: «подключить данного клиента к очереди `test1` в качестве отправителя».

Пример:

```text
receive test1\n
```

означает: «подключить данного клиента к очереди `test1` в качестве получателя».

Требования к строке настройки:

- команда и имя очереди разделены одним пробелом;
- строка заканчивается символом `\n`;
- имя очереди состоит из символов `A-Z`, `a-z`, `0-9`, `_`, `-`;
- после отправки строки необходимо выполнить `flush()`;
- режим работы не изменяется, пока соединение открыто.

## 2.2. Сообщения

Сообщение состоит из заголовка и полезной нагрузки:

```text
message <length>\n<payload>
```

где:

- `message` — команда;
- `<length>` — длина полезной нагрузки **в байтах**;
- `<payload>` — ровно `<length>` байтов.

Пример:

```text
message 12\nHello world!
```

Строка `Hello world!` занимает 12 байтов, поэтому в заголовке указано `12`.

Тот же формат используется в обоих направлениях:

- отправитель → сервер;
- сервер → получатель.

## 2.3. Кадрирование

При чтении сообщения необходимо:

1. прочитать заголовок до символа `\n`;
2. разобрать число — длину в байтах;
3. прочитать ровно `<length>` байтов полезной нагрузки;
4. декодировать байты как UTF-8.

Важные следствия:

- полезная нагрузка может содержать любые байты, в том числе `\n`; ориентироваться на длину, а не на перевод строки;
- `readLine()` для полезной нагрузки использовать нельзя;
- нельзя создавать два разных объекта чтения поверх одного `InputStream`: буферизованное чтение может «забрать» байты, которые нужны следующему читателю;
- длина — это именно байты, а не символы. Для строки `привет` длина равна 12, а не 6;
- при отправке используйте `message.getBytes(StandardCharsets.UTF_8).length`, а не `message.length()`.

Именно на этом месте чаще всего возникают ошибки, которые проявляются только на не-ASCII тексте или при быстрой отправке нескольких сообщений подряд.

## 2.4. Ошибки и завершение

Базовый протокол не содержит подтверждений. Поэтому клиент должен как минимум корректно обрабатывать следующие ситуации:

- сервер недоступен (соединение не установлено);
- соединение разорвано во время чтения;
- заголовок имеет неверный формат;
- длина в заголовке некорректна;
- получено меньше байтов, чем указано в заголовке (обрыв);
- истёк таймаут ожидания сообщений.

Клиент не должен «зависать» навсегда и не должен молча терять ошибку в фоновом потоке.

## 2.5. Отличие от лекционного примера

В лекционном примере использовалась упрощённая команда `msg`, а длина трактовалась как число символов. В лабораторной используется команда `message`, а длина всегда задаётся в байтах. Если вы берёте код из лекции, адаптируйте его под протокол из этого раздела.

# 3. Минимальный клиент

Ниже приведён минимальный пример, демонстрирующий установку режима и чтение одного сообщения. Это **не** итоговый клиент: в нём нет фонового приёма, таймаутов, потокобезопасного хранилища и полноценной обработки ошибок.

```java
import java.io.ByteArrayOutputStream;
import java.io.EOFException;
import java.io.IOException;
import java.io.InputStream;
import java.io.OutputStream;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class Main {

    public static void main(String[] args) throws IOException {
        String host = "localhost";
        int port = 1111;
        String queue = "test";
        String mode = args.length > 0 ? args[0] : "receive";

        try (Socket socket = new Socket(host, port)) {
            OutputStream out = socket.getOutputStream();
            InputStream in = socket.getInputStream();

            if ("send".equals(mode)) {
                out.write(("send " + queue + "\n")
                        .getBytes(StandardCharsets.US_ASCII));
                out.flush();

                sendMessage(out, "Hello world!");
            } else {
                out.write(("receive " + queue + "\n")
                        .getBytes(StandardCharsets.US_ASCII));
                out.flush();

                System.out.println("Received: " + readMessage(in));
            }
        }
    }

    static void sendMessage(OutputStream out, String message) throws IOException {
        byte[] payload = message.getBytes(StandardCharsets.UTF_8);

        out.write(("message " + payload.length + "\n")
                .getBytes(StandardCharsets.US_ASCII));
        out.write(payload);
        out.flush();
    }

    static String readMessage(InputStream in) throws IOException {
        String header = readLine(in);

        if (header == null) {
            throw new EOFException("connection closed");
        }

        if (!header.startsWith("message ")) {
            throw new IOException("unexpected header: " + header);
        }

        int length = Integer.parseInt(header.substring("message ".length()));
        byte[] payload = in.readNBytes(length);

        if (payload.length != length) {
            throw new EOFException("short payload");
        }

        return new String(payload, StandardCharsets.UTF_8);
    }

    static String readLine(InputStream in) throws IOException {
        ByteArrayOutputStream buffer = new ByteArrayOutputStream();

        int b;

        while ((b = in.read()) != -1) {
            if (b == '\n') {
                return buffer.toString(StandardCharsets.US_ASCII);
            }

            if (b != '\r') {
                buffer.write(b);
            }

            if (buffer.size() > 1024) {
                throw new IOException("header too long");
            }
        }

        if (buffer.size() == 0) {
            return null;
        }

        return buffer.toString(StandardCharsets.US_ASCII);
    }
}
```

### Что демонстрирует пример

- установку режима работы одной строкой;
- отправку кадра `message <length>\n<payload>`;
- чтение заголовка и полезной нагрузки;
- проверку длины и обработку обрыва;
- использование UTF-8 для полезной нагрузки.

### Чем этот пример не является

Это не клиентская библиотека и не решение лабораторной. В нём:

- нет фонового потока приёма;
- нельзя принять больше одного сообщения;
- нет хранения принятых сообщений;
- нет ожидания с таймаутом;
- нет потокобезопасности;
- нет корректного закрытия и освобождения ресурсов;
- нет автоматических сценариев тестирования.

# 4. Требования к итоговому клиенту

Итоговый клиент должен быть оформлен как отдельный класс, пригодный для использования в многопоточной программе.

## 4.1. Рекомендуемый интерфейс

Конкретные имена методов могут отличаться, но поведение должно быть эквивалентным.

```java
public final class BrokerClient implements AutoCloseable {

    public enum Role {
        SENDER,
        RECEIVER
    }

    public BrokerClient(String host, int port, Role role, String queue)
            throws IOException;

    public void send(String message) throws IOException;

    public List<String> receive(int count, Duration timeout)
            throws InterruptedException, IOException;

    public void close() throws IOException;
}
```

## 4.2. Установка соединения

В конструкторе клиент должен:

1. открыть TCP-соединение с сервером;
2. отправить строку `send <queue>\n` или `receive <queue>\n`;
3. выполнить `flush()`;
4. проверить, что роль и имя очереди корректны;
5. для получателя — запустить фоновый поток чтения.

Если соединение установить не удалось, конструктор должен выбросить понятное исключение, а не оставить клиент в нерабочем состоянии.

## 4.3. Отправка сообщений

Метод `send` должен:

- кодировать сообщение в UTF-8;
- вычислять длину в байтах;
- записывать заголовок и полезную нагрузку;
- выполнять `flush()` после каждого сообщения;
- быть потокобезопасным, если предполагается вызов из нескольких потоков.

Если несколько потоков вызывают `send` одновременно, запись заголовка и полезной нагрузки не должна перемешиваться. Допустимые варианты:

- `synchronized` на методе или на отдельном объекте-блокировке;
- отдельный поток-писатель и очередь исходящих сообщений.

## 4.4. Приём сообщений

Для получателя необходимо:

- запустить фоновый поток, который непрерывно читает кадры;
- складывать принятые строки в потокобезопасную очередь;
- при разрыве соединения завершить поток и сохранить информацию об ошибке;
- не терять ошибки: ожидающий поток должен узнать о проблеме.

Хранение принятых сообщений должно быть потокобезопасным. Подходящие варианты:

```java
BlockingQueue<String> received = new LinkedBlockingQueue<>();
```

или:

```java
List<String> received = Collections.synchronizedList(new ArrayList<>());
```

Но во втором случае необходимо дополнительно синхронизировать составные операции и не отдавать внутренний список наружу.

## 4.5. Ожидание сообщений с таймаутом

Метод `receive(count, timeout)` должен:

- вернуть не более `count` сообщений;
- вернуться, как только набрано `count` сообщений;
- вернуться по истечении таймаута, даже если сообщений меньше;
- не использовать `Thread.sleep()` как способ ожидания;
- выбрасывать исключение, если соединение разорвано или произошла ошибка протокола.

Ожидание удобно реализовать через `BlockingQueue.poll(timeout, unit)` в цикле до достижения нужного количества или до истечения общего дедлайна.

## 4.6. Завершение работы

Метод `close()` должен:

- быть идемпотентным (повторный вызов не должен падать);
- закрыть сокет;
- прервать и дождаться фонового потока чтения;
- не оставлять работающих потоков после завершения.

Если `close()` вызывается из фонового потока, нельзя выполнять `join()` этого же потока.

## 4.7. Обработка ошибок

Клиент не должен:

- выбрасывать исключение из фонового потока и «терять» его;
- молча игнорировать обрыв соединения;
- бесконечно ждать сообщение, которое уже не придёт.

Рекомендуется хранить последнюю ошибку в поле и проверять её в `receive()` и `send()`.

## 4.8. Ограничения

Клиент должен:

- отклонять пустые и слишком большие сообщения (например, больше 1 МиБ);
- отклонять некорректные имена очередей;
- ограничивать длину заголовка (например, 1024 байта);
- корректно обрабатывать отрицательную и нулевую длину.

# 5. Обязательные сценарии тестирования

Клиент при запуске должен автоматически выполнять три сценария. Все сценарии выполняются в одном процессе: отправители и получатели — это объекты `BrokerClient`, запускаемые в отдельных потоках.

Перед запуском тестов сервер должен быть уже запущен. Для управления порядком подключения (например, «получатель подключается после первых 500 сообщений») используйте `CountDownLatch`, а не `Thread.sleep()`.

Общие требования:

- для каждого сценария используется своё имя очереди, например `lab4-s1-<время>`, чтобы прогоны не влияли друг на друга;
- каждое сообщение содержит уникальный идентификатор, например `s1-000001:<случайный текст>`;
- получатель извлекает идентификатор и складывает его в потокобезопасное множество;
- дубликаты фиксируются отдельно;
- таймаут каждого сценария — 10 секунд с момента первой отправки;
- по завершении сценария печатается итог: отправлено, получено, потеряно, дубликатов, время, результат `PASS`/`FAIL`;
- если сценарий завершился ошибкой, программа должна завершиться с ненулевым кодом возврата.

Сводная таблица сценариев:

| № | Отправителей | Получателей | Сообщений | Особенность |
|--:|-------------:|------------:|----------:|-------------|
| 1 | 1 | 1 | 1000 (500 + 500) | получатель подключается после первых 500 |
| 2 | 1 | 2 | 1000 | первый получатель отключается после 250 |
| 3 | 2 | 3 | 2000 | вывод процентов по получателям |

## 5.1. Сценарий 1. Один отправитель и один получатель

Порядок действий:

1. отправитель подключается к очереди;
2. отправитель отправляет 500 случайных сообщений;
3. к той же очереди подключается получатель;
4. отправитель отправляет ещё 500 сообщений и завершает работу;
5. получатель ждёт до 10 секунд, пока не получит 1000 сообщений.

Критерий успеха:

- получено ровно 1000 сообщений;
- все идентификаторы уникальны;
- множество полученных идентификаторов совпадает с множеством отправленных;
- потерь и дубликатов нет.

Критерий ошибки:

- получено меньше 1000 сообщений за 10 секунд;
- обнаружены дубликаты;
- обнаружены потерянные сообщения;
- возникло исключение.

Смысл сценария: проверить, что сообщения, отправленные до подключения получателя, накапливаются в очереди и не теряются.

## 5.2. Сценарий 2. Один отправитель и два получателя

Порядок действий:

1. получатели `R1` и `R2` подключаются к очереди;
2. отправитель подключается к той же очереди;
3. отправитель отправляет 1000 сообщений;
4. `R1` принимает 250 сообщений и закрывает соединение;
5. `R2` работает до тех пор, пока суммарно `R1` и `R2` не получат 1000 сообщений, либо до истечения 10 секунд.

Критерий успеха:

- суммарно получено 1000 уникальных сообщений;
- дубликатов нет;
- `R1` получил ровно 250 сообщений;
- `R2` получил оставшиеся 750 сообщений;
- потерь нет.

Критерий ошибки:

- суммарно получено меньше 1000 сообщений;
- обнаружены дубликаты;
- сообщение потеряно при отключении `R1`;
- возникло исключение.

Смысл сценария: проверить, что отключение одного получателя не приводит к потере сообщений и что оставшийся получатель забирает оставшуюся часть очереди.

## 5.3. Сценарий 3. Два отправителя и три получателя

Порядок действий:

1. получатели `R1`, `R2`, `R3` подключаются к очереди;
2. отправители `S1` и `S2` подключаются к той же очереди;
3. каждый отправитель отправляет по 1000 сообщений (всего 2000);
4. получатели работают до тех пор, пока суммарно не будет получено 2000 сообщений, либо до истечения 10 секунд;
5. после завершения выводится количество и процент сообщений, полученных каждым получателем.

Критерий успеха:

- суммарно получено 2000 уникальных сообщений;
- дубликатов нет;
- потерь нет;
- выведены проценты по каждому получателю;
- сумма процентов равна 100%.

Критерий ошибки:

- суммарно получено меньше 2000 сообщений;
- обнаружены дубликаты или потери;
- возникло исключение.

Пример вывода:

```text
Scenario 3: 2 senders, 3 receivers
Sent:      2000
Received:  2000
Duplicate: 0
Lost:      0
Time:      1.842 s

Receiver shares:
  R1:  671  33.55%
  R2:  664  33.20%
  R3:  665  33.25%

Result: PASS
```

Точное равенство долей не требуется: сервер распределяет сообщения конкурентно, поэтому небольшой разброс нормален. Однако при большом отклонении (например, один получатель получил менее 20% при трёх получателях) стоит проверить, не является ли распределение неравномерным.

# 6. Методика измерений

Для каждого сценария необходимо фиксировать:

- количество отправленных сообщений;
- количество полученных сообщений;
- количество потерянных сообщений;
- количество дубликатов;
- время выполнения;
- результат `PASS`/`FAIL`.

Время измеряется с момента отправки первого сообщения до момента получения последнего ожидаемого сообщения. Для измерений используйте `System.nanoTime()`.

Пропускная способность:

$$
X = \frac{N}{T},
$$

где:

- $N$ — количество доставленных сообщений;
- $T$ — время выполнения в секундах.

Единица измерения — сообщений в секунду (`msg/s`).

Доля получателя:

$$
p_i = \frac{N_i}{N} \cdot 100\%,
$$

где $N_i$ — количество сообщений, полученных получателем $i$.

Для оценки равномерности можно использовать максимальное отклонение доли от идеальной:

$$
D = \max_i \left| p_i - \frac{100\%}{M} \right|,
$$

где $M$ — количество получателей.

### Требования к измерениям

**Один запуск не является достаточным экспериментом.**

Рекомендуется:

1. выполнить один прогревочный запуск;
2. выполнить не менее 5 измерений для каждого сценария;
3. для итогового сравнения использовать медиану или минимальное время;
4. использовать одинаковую методику для всех вариантов.

Результаты рекомендуется сохранять в файл `results/measurements.csv`:


# 14. Итоговая схема работы

```text
                    BrokerClient
                         │
          ┌──────────────┴──────────────┐
          │                             │
       SENDER                       RECEIVER
          │                             │
   send(queue)                    background reader
          │                             │
  message <len>\n<payload>       BlockingQueue<String>
          │                             │
          └──────────→ Broker ←─────────┘
                         │
                 очередь по имени
                         │
              распределение между
                 получателями
```

Клиент должен уметь работать в обоих режимах, корректно кадрировать сообщения, не терять данные при конкурентном доступе и предоставлять удобный способ дождаться нужного количества сообщений с таймаутом.
